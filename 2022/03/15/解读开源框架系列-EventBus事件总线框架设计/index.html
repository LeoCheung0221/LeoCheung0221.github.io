一、EventBus 概述与设计动机

EventBus 是 Android 生态中最流行的事件总线框架之一，由 greenrobot 开发维护。它的核心思想是发布-订阅模式（Publish-Subscribe Pattern）——让组件之间以事件为媒介进行松耦合通信，避免 Activity/Fragment/Service 之间的强依赖。

与 Android 原生的跨组件通信方式相比：

  • Intent / BroadcastReceiver：依赖系统级 IPC，性能开销大，且需要序列化数据。
  • Handler / Message：需要持有对方的引用，耦合度高，且不支持一对多广播。
  • 接口回调（Callback）：需要定义接口并持有引用，随着业务复杂化会陷入回调地狱。
  • EventBus：零配置的发布订阅，一行注解即可，且线程调度灵活。

EventBus 的 GitHub 仓库是 https://github.com/greenrobot/EventBus。本文基于 EventBus 3.x 源码分析，核心源码包路径为 org.greenrobot.eventbus。

1.1 发布-订阅模式的三种变体

类型 通信方式 EventBus 支持 典型场景
普通事件 发布后所有已注册订阅者收到 支持（post） 用户登录状态变更通知
粘性事件 发布时缓存，后注册的也能收到 支持（postSticky） 先加载数据，后打开页面

注意 subscriptionsByEventType 使用 CopyOnWriteArrayList，这是一种在遍历时不加锁的并发容器，非常适合读多写少的订阅分发场景。

为什么用 CopyOnWriteArrayList 而不是 ConcurrentHashMap 的并发集合？

CopyOnWriteArrayList 的核心特性是：每次修改（add、set、remove）都会创建底层数组的新副本。这保证了遍历操作的线程安全性——迭代器持有的是快照，不受并发修改影响。EventBus 的订阅分发（post）是纯读操作（遍历 subscriptions 列表），而注册/注销（register/unregister）是相对低频的写操作——这正是 COW 的最佳场景。

五、线程模式（ThreadMode）详解

EventBus 定义了五种线程模式，这是其最精妙的设计之一：

模式 说明 内实现 典型场景
POSTING 与 post() 在同一线程执行，开销最小 直接反射调用 无 UI 操作的纯数据更新
MAIN 在主线程执行 通过 Handler 切换到主线程 更新 UI
MAIN_ORDERED 在主线程执行，按入队顺序串行 队列 + Handler 需要严格顺序的 UI 操作
BACKGROUND 在后台线程执行（单线程池） Single-thread Executor 避免并发写数据库
ASYNC 在任意线程池线程执行 Cached Thread Pool 完全解耦，不阻塞任何一方

5.1 POSTING vs MAIN 的线程安全考量

POSTING 模式下，事件处理与 post() 在同一线程执行。如果在事件处理方法中执行了耗时操作（如网络请求），会阻塞 post() 所在线程。关键陷阱：如果在主线程 post 了事件，并用 POSTING 模式处理事件，处理逻辑必须极快（< 5ms），否则会导致主线程卡顿。

六、粘性事件（Sticky Events）

粘性事件是一种特殊的投递机制：事件在发送时被缓存，后续注册的订阅者也能收到之前发送的事件。这在某些场景非常有用，比如先加载了数据，后续打开的 Fragment 仍能获取到数据。

8.1 迁移策略：EventBus → LiveData/Flow

如果你的项目逐渐使用 Jetpack MVVM 架构，可以按以下策略迁移：

  1. ViewModel 内部：用 StateFlow 替代 EventBus 在 ViewModel 之间的通信
  2. 同一 Activity/Fragment 内：用 LiveData 替代 EventBus 传递 UI 事件
  3. 跨模块通信：保留 EventBus 作为模块间松耦合的通信方案，或使用 SharedFlow 的 shareIn + CoroutineScope

九、面试常问题目

Q1: EventBus 注册时为什么要遍历父类？

因为 @Subscribe 注解的方法可能在父类中定义（如 BaseActivity 中定义了通用的事件处理方法）。通过遍历从子类到 Object 的整个继承链，确保所有父类的订阅方法都被注册。FindState 通过 moveToSuperclass() 向上递归，直到 skipSuperClasses 被设为 true。

Q2: EventBus 的 post() 方法是线程安全的吗？如何保证？

是线程安全的。通过 ThreadLocal<PostingThreadState> 为每个线程维护独立的事件队列，避免锁竞争。CopyOnWriteArrayList 用于存储订阅者列表，写入时复制，遍历时不加锁，是高并发的经典优化手段。另外，stickyEvents 的读写使用 synchronized 保护。

Q3: EventBus 为什么不使用动态代理（如 Retrofit 的方式）？

动态代理需要接口定义，而 EventBus 的设计目标是零配置——用户只需在任意方法上加 @Subscribe 注解即可。使用反射直接调用 Method 是最直接的方式。编译期索引（Subscriber Index）通过 APT 在编译时生成元数据，规避了运行时反射的性能开销。

Q4: 粘性事件如何避免内存泄漏？

粘性事件存储在 stickyEvents Map 中，Key 是事件类型 Class 对象（不会被 GC），Value 是事件实例。最好的实践是：事件处理完后调用 EventBus.getDefault().removeStickyEvent(eventClass) 移除粘性事件。也可以使用 removeAllStickyEvents() 清空所有粘性事件。注意不要在粘性事件中持有 Activity/Fragment 引用。

Q5: EventBus 3.x 相比 2.x 的核心改进是什么？

(1) 编译期索引（Subscriber Index）——避免反射扫描，提升注册速度；(2) 类型安全的 @Subscribe 注解替代命名约定（不再要求方法名必须是 onEvent 等）；(3) ThreadMode 的粒度更细（增加了 MAIN_ORDERED）；(4) 对象池（PendingPost 复用）减少 GC 压力；(5) 全局错误处理（EventBusException 链）比 2.x 的静默吞错误更易调试。
